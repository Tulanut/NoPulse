The Local-First Data Mutation & Inline Editing Playbook

How to Methodically Add Edit & Weight Correction Capabilities to Historical Data Across an Offline-First Full-Stack App
Audience: Junior Software Engineers & Developers

1. The Challenge: Why "Just Make It Editable" is Deceptive

In a real-world software engineering job, your manager or client will often say:

Employer Request: "In the exercise history view, users sometimes type the wrong weight or reps. Allow them to edit existing logged workouts and change their weight."

To an inexperienced developer, this sounds like a 5-minute task: add an edit button, open a JavaScript prompt(), and call setState(). But in a local-first, offline-capable production application, historical data mutations trigger a cascade across the entire system:

  • Derived Statistics Invalidation: An exercise displays a Personal Record (PR) / Max Weight, a Total Reps counter, and a Volume Progression Chart. Editing a workout from 3 weeks ago must recompute all these calculations instantly in the UI.
  • Offline-First Resilience: If a user is in a gym basement without reception, edits must write immediately to IndexedDB, mark the record as sync_status: 'pending', and update the updated_at timestamp so Last-Write-Wins synchronization works cleanly.
  • Backend Contract & Validation: The server needs an idempotent PUT /api/workouts/:id endpoint that validates inputs (positive sets/reps, null vs. numeric weights) and safely updates the database.
  • Mobile Ergonomics: Screen-blocking popups fight with the on-screen keyboard. A smooth, accessible inline edit card with +2.5 / -2.5 weight steppers provides a far superior user experience.

2. The Mental Model: Newbie Chaos vs. Senior Method

❌ The Newbie Approach (Outside-In Chaos)

1. Starts in the UI: Adds local useState in the leaf view component.

2. Mutates State Directly: Sets workout.weight = 80 in place, breaking React immutability.

3. Skips Offline Storage: Edits vanish on page reload because IndexedDB was never notified.

4. Skips Timestamps: Doesn't bump updated_at, causing the sync engine to overwrite the user's edits with older server data.

5. Stale Graphs: Volume charts and PR badges stay stuck on old numbers.

✅ The Senior Method (Inside-Out Discipline)

1. API Contract First: Implements PUT /api/workouts/:id with input validation and timestamp bumping.

2. State Engine & IDB: Writes updateWorkout() in useWorkouts.ts, saving to IndexedDB with pending status.

3. Reactive Derivation: Leverages useMemo so all PRs and charts recalculate automatically.

4. Dual-Mode UI: Builds a 1-tap quick weight click badge and a full inline card with steppers.

5. Clean Builds: Verifies client and server compile with 0 TypeScript errors.

4. Step-by-Step Implementation Breakdown

1
Stage 1: The Backend Contract & Data Mutation API (Express + SQLite)

Never mutate data on the client without having an idempotent server endpoint ready to receive it. In server/src/controllers/workoutController.ts:

static updateWorkout(req: Request, res: Response): void {
  try {
    const { id } = req.params;
    const existing = db.getWorkoutById(id);
    if (!existing) {
      res.status(404).json({ error: 'Workout not found' });
      return;
    }

    const { exercise, sets, reps, weight, fatigue, profile, sub_profile, date, notes } = req.body;

    const parsedSets = sets !== undefined ? Number(sets) : existing.sets;
    const parsedReps = reps !== undefined ? Number(reps) : existing.reps;
    if (parsedSets < 1 || parsedReps < 1) {
      res.status(400).json({ error: 'Sets and reps must be positive integers' });
      return;
    }

    const parsedWeight = weight !== undefined
      ? (weight === null || weight === '' ? null : Number(weight))
      : existing.weight;

    const updatedWorkout: Workout = {
      ...existing,
      exercise: exercise !== undefined ? String(exercise).trim() : existing.exercise,
      sets: parsedSets,
      reps: parsedReps,
      weight: parsedWeight,
      fatigue: fatigue !== undefined ? fatigue : existing.fatigue,
      profile: profile !== undefined ? String(profile).trim() : existing.profile,
      sub_profile: sub_profile !== undefined ? (sub_profile ? String(sub_profile).trim() : null) : existing.sub_profile,
      date: date !== undefined ? String(date) : existing.date,
      notes: notes !== undefined ? (notes ? String(notes) : null) : existing.notes,
      updated_at: new Date().toISOString(), // CRITICAL: Bump timestamp for Last-Write-Wins sync
    };

    db.upsertWorkout(updatedWorkout);
    res.json({ workout: updatedWorkout });
  } catch (error) {
    res.status(500).json({ error: 'Failed to update workout' });
  }
}

Mount the route in server/src/routes/workoutRoutes.ts:

router.put('/workouts/:id', WorkoutController.updateWorkout);
2
Stage 2: Client State Engine & Offline Sync Queue (useWorkouts.ts)

The UI component should never talk to the network directly. Instead, delegate to the state hook to update in-memory state and the offline database atomically:

const updateWorkout = useCallback(
  async (id: string, updates: Partial<Omit<Workout, 'id' | 'created_at'>>) => {
    try {
      const existing = workouts.find((w) => w.id === id);
      if (!existing) throw new Error(`Workout with id ${id} not found`);

      const updatedRecord: Workout = {
        ...existing,
        ...updates,
        updated_at: new Date().toISOString(),
        sync_status: 'pending', // Marks for background sync
      };

      // 1. Optimistic in-memory update
      setWorkouts((prev) => prev.map((w) => (w.id === id ? updatedRecord : w)));

      // 2. Persist to browser IndexedDB
      await localDB.saveWorkout(updatedRecord);

      // 3. Register any new profile or sub-profile
      if (updates.profile && !profiles.includes(updates.profile)) {
        await addProfile(updates.profile);
      }
      if (updates.profile && updates.sub_profile) {
        await addSubProfile(updates.profile, updates.sub_profile);
      }

      // 4. Refresh & trigger background sync if online
      await refreshLocalWorkouts();
      if (navigator.onLine) {
        syncService.runSync().catch(console.error);
      }

      return updatedRecord;
    } catch (err) {
      console.error('Failed to update workout:', err);
      throw err;
    }
  },
  [workouts, profiles, addProfile, addSubProfile, refreshLocalWorkouts]
);
3
Stage 3: Reactive State Propagation & Downstream Invalidation

Avoid manually updating PR cards or chart states. By deriving them with useMemo from allWorkouts, changing any workout automatically triggers a flawless recalculation:

// In ExerciseDetailView.tsx:
const exerciseWorkouts = useMemo(() => {
  return allWorkouts
    .filter((w) => w.exercise.toLowerCase() === exerciseName.toLowerCase())
    .sort((a, b) => new Date(b.date).getTime() - new Date(a.date).getTime());
}, [allWorkouts, exerciseName]);

// Derived PR & totals recalculate automatically:
const stats = useMemo(() => {
  const maxWeight = Math.max(...exerciseWorkouts.map((w) => w.weight || 0), 0);
  const totalReps = exerciseWorkouts.reduce((acc, w) => acc + w.sets * w.reps, 0);
  return { maxWeight, totalReps, totalLogs: exerciseWorkouts.length };
}, [exerciseWorkouts]);

Stage 5: Dual-Mode UI/UX & Inline Edit Design (ExerciseDetailView.tsx)

We built two intuitive ways to initiate editing:

  • Quick-Click Weight Badge: Clicking @ {workout.weight} kg immediately opens edit mode with the weight input focused for rapid correction.
  • Dedicated Pencil Button: Sits next to the Delete button for editing sets, reps, fatigue, dates, or moving between sub-folders.
  • Inline Edit Card: Features high-precision -2.5 / +2.5 stepper buttons, RIR pills, keyboard shortcuts (Enter to save, Escape to cancel), and feedback toast alerts.

6. Top 5 Traps That Break Production Mutations

Trap 1: String Concatenation on Numbers ("80" + 2.5 = "802.5")

HTML input fields always yield strings. If you add + 2.5 directly, JavaScript converts the operation into string concatenation. Always use parseFloat() before doing arithmetic.

Trap 2: In-Place Array Mutation (workouts[i] = updated)

Modifying an array in place does not change the array's object identity in memory. React will assume the state is unchanged and skip re-rendering. Always use prev.map(...).

Trap 3: Forgetting to Bump updated_at

If you edit a record without updating updated_at, the sync engine will treat the edit as older than the remote record during the next sync cycle and silently overwrite your changes.

Trap 4: Screen-Obscuring Modals on Mobile

Centered popups are frequently covered by mobile virtual keyboards, hiding the Save button. An inline expandable card ensures the browser scrolls the active field smoothly into view.

Trap 5: Duplicate Stored State for Calculated Statistics

Never store calculated metrics (like Max Weight or Total Reps) in separate states that require manual sync functions. Derive them directly from raw records with useMemo so they never go out of date.
