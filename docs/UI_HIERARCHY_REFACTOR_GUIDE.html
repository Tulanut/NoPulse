UI Hierarchy & Design Symmetry Playbook

How to Methodically Refactor Nested UI Components to Match Existing Design Systems Without Mess, Regressions, or Confusion
Target: Junior Software Engineers & Full-Stack Developers

1. The Challenge: "Make Feature X Look Exactly Like Page Y"

In commercial software development, an employer, product manager, or lead designer will frequently hand you this requirement:

Real-World Request:
"The sub-folder horizontal chip toolbar we built feels cramped and confusing. Redesign sub-folders so they look and behave the exact same way as workout profile cards on the front page. Keep it minimalistic, familiar, and clean."

To an inexperienced developer, this sounds deceptively simple: "Just change the styling." But turning a horizontal filter bar into a hierarchical card grid with drilldown levels fundamentally alters:

  • View States: Expanding the screen from 2 visual tiers to 3 distinct depth levels.
  • Search Scoping: Determining whether search filters the entire profile or just the active sub-folder.
  • Drop Targets: Defining where an exercise moves when dropped on cards versus back buttons.
  • State Cleanup: Resetting selections, searches, and drilldowns safely upon back navigation or deletion.
  • Mobile Parity: Preserving touch-friendly drag haptics, sticky drop trays, and 1-tap sheet modals.

2. The Mindset Shift: Newbie Chaos vs. Senior Method

❌ The Newbie Anti-Pattern

Ad-hoc Copy-Paste & Fragmented State:

  • Copies JSX blocks blindly from the front page without understanding underlying data dependencies.
  • Nests ternary operators (? : ? :) 4 levels deep, creating unmaintainable JSX and brace-matching compile errors.
  • Calculates counts inline inside loops, causing re-render lag.
  • Slightly alters Tailwind classes, resulting in mismatched padding, borders, and an amateurish feel.
✅ The Senior Discipline

Data Symmetry & Finite State Drilldowns:

  • Data Symmetry: Mirrors the front page card model (subProfileCards derived with identical fields to profileCards).
  • FSM Early Returns: Separates views cleanly using early returns instead of nested ternaries.
  • Predictable DND: Treats every card and back button as a bidirectional state transition.
  • Compile-First Rhythm: Verifies TypeScript compilation (tsc -b) after each structural modification.

3. The 3-Tier Hierarchical Mental Model

A methodical frontend engineer views multi-level drilldowns as a Finite State Machine (FSM) with 3 distinct tiers:

========================================================================================
[ Tier 0: Global Exercises Hub ]  (activeProfile === null)
  ├── Global Header (Exercises title, global search, bulk select)
  ├── WORKOUT PROFILE CARDS GRID (2-column: Armwrestling, Push, Pull...)
  └── General / Uncategorized Exercises List
       │
       ▼ (User clicks a Profile Card -> setActiveProfile("Armwrestling"))
========================================================================================
[ Tier 1: Profile Root View ]  (activeProfile !== null && activeSubProfile === null)
  ├── "← Back to Exercises" Button (Drop target to remove exercise back to General)
  ├── Profile Header (Editable title, delete profile, profile-wide search)
  ├── SUB-FOLDERS CARDS GRID (Exact same 2-column card design: Sleep Day, Heavy Day...)
  │    └── "+ New Sub-Folder" inline form
  └── General Exercises in this Profile
       │
       ▼ (User clicks a Sub-Folder Card -> setActiveSubProfile("Sleep Day"))
========================================================================================
[ Tier 2: Sub-Folder Drilldown View ]  (activeProfile !== null && activeSubProfile !== null)
  ├── "← Back to Armwrestling" Button (Drop target to remove exercise back to Profile Root)
  ├── Sub-Folder Header (Editable sub-folder title, delete sub-folder, scoped search)
  └── Exercises in this Sub-Folder List
========================================================================================

The Drag-and-Drop Mutation Matrix

Current Tier Dragged Item Drop Target State Mutation Triggered
Tier 0 (Front Page) Any Exercise Profile Card [X] onBulkUpdateExerciseProfile([item], "X")
Tier 1 (Profile Root) Profile Exercise Sub-Folder Card [Y] onUpdateExerciseSubProfile(item, activeProfile, "Y")
Tier 1 (Profile Root) Profile Exercise ← Back to Exercises Button onBulkUpdateExerciseProfile([item], null) (Reverts to General)
Tier 2 (Sub-Folder) Sub-Folder Exercise ← Back to {Profile} Button onUpdateExerciseSubProfile(item, activeProfile, null) (Reverts to Profile Root)

4. Step-by-Step Implementation Flow (The Exact Sequence)

Step 1 Symmetry in Data Derivation (useMemo Cards)

Before writing a single line of JSX, derive a symmetric data structure. If Tier 0 derives profileCards, Tier 1 must derive subProfileCards with the exact same interface:

// client/src/components/ExerciseHub.tsx
const subProfileCards = useMemo(() => {
  if (!activeProfile) return [];
  const subMap = new Map<string, { count: number; exerciseSet: Set<string> }>();

  // 1. Seed with known sub-profiles (Guarantees empty folders still render!)
  currentSubProfiles.forEach((s) => {
    subMap.set(s, { count: 0, exerciseSet: new Set() });
  });

  // 2. Aggregate logs and unique exercise names
  activeProfileWorkouts.forEach((w) => {
    if (w.sub_profile) {
      if (!subMap.has(w.sub_profile)) {
        subMap.set(w.sub_profile, { count: 0, exerciseSet: new Set() });
      }
      const entry = subMap.get(w.sub_profile)!;
      entry.count++;
      entry.exerciseSet.add(w.exercise);
    }
  });

  // 3. Normalize into uniform card objects
  return Array.from(subMap.entries()).map(([name, data]) => ({
    name,
    totalLogs: data.count,
    uniqueExercises: data.exerciseSet.size,
  }));
}, [activeProfile, currentSubProfiles, activeProfileWorkouts]);

Step 2 Scoping Search & Exercise Filtering Across Tiers

Search ambiguity frustrates users. Build predictable search scoping into currentSummaries:

const currentSummaries = useMemo(() => {
  if (activeProfile) {
    // Tier 2: Drilled into Sub-Folder -> Strict filter
    if (activeSubProfile) {
      const filtered = activeProfileWorkouts.filter(
        (w) => w.sub_profile?.toLowerCase() === activeSubProfile.toLowerCase()
      );
      return sortWithCustomOrder(groupExercises(filtered));
    }

    // Tier 1: At Profile Root WITH Search -> Search across ENTIRE profile
    if (searchQuery.trim()) {
      return sortWithCustomOrder(groupExercises(activeProfileWorkouts));
    }

    // Tier 1: At Profile Root WITHOUT Search -> Show only root exercises
    const rootExercises = activeProfileWorkouts.filter((w) => !w.sub_profile);
    return sortWithCustomOrder(groupExercises(rootExercises));
  }

  // Tier 0: Front Page -> Uncategorized exercises
  const list = profileCards.length > 0 ? uncategorizedWorkouts : workouts;
  return sortWithCustomOrder(groupExercises(list));
}, [activeProfile, activeSubProfile, activeProfileWorkouts, searchQuery, profileCards.length, uncategorizedWorkouts, workouts, customOrder]);

Step 3 View Orchestration & Drilldown Routing (FSM Architecture)

Replace massive nested ternaries with early returns:

// VIEW 1: INSIDE A WORKOUT PROFILE
if (activeProfile) {
  // SUB-VIEW 1B: DRILLDOWN INTO A SUB-FOLDER (Tier 2)
  if (activeSubProfile) {
    return (
      <div className="subfolder-drilldown space-y-10">
        {/* Back Button -> setActiveSubProfile(null) */}
        {/* Sub-Folder Header (Editable name, delete confirmation) */}
        {/* Exercises List in Sub-Folder */}
        {renderBulkActionBar()}
      </div>
    );
  }

  // SUB-VIEW 1A: PROFILE ROOT (Tier 1)
  return (
    <div className="profile-root space-y-10">
      {/* Back Button -> setActiveProfile(null) */}
      {/* Profile Header */}
      {/* SUB-FOLDERS CARDS GRID (Mirrors front page) */}
      {/* GENERAL EXERCISES LIST */}
      {renderBulkActionBar()}
    </div>
  );
}

// VIEW 2: GLOBAL EXERCISE HUB (Tier 0)
return (
  <div className="global-hub space-y-10">
    {/* Global Header */}
    {/* WORKOUT PROFILE CARDS GRID */}
    {/* General Exercises List */}
    {renderBulkActionBar()}
  </div>
);

Step 5 Drag-and-Drop Drop-Target Matrix

Make cards and back buttons dual-purpose: clickable navigation links AND drag-and-drop drop targets.

<!-- Back Button that removes an exercise from a sub-folder when dropped on it -->
<button
  onClick={() => setActiveSubProfile(null)}
  data-subprofile-drop="__none__"
  onDragOver={(e) => {
    e.preventDefault();
    setDragOverSubProfile('__none__');
  }}
  onDrop={async (e) => {
    e.preventDefault();
    const exercise = e.dataTransfer.getData('text/plain') || draggingExercise;
    if (exercise && onUpdateExerciseSubProfile && activeProfile) {
      await onUpdateExerciseSubProfile(exercise, activeProfile, null);
      setDragFeedbackMessage(`Removed "${exercise}" from "${activeSubProfile}"`);
    }
    setDraggingExercise(null);
  }}
>
  <ArrowLeft className="w-4 h-4" />
  <span>{draggingExercise ? `📥 Drop here to move back to ${activeProfile}` : `Back to ${activeProfile}`}</span>
</button>

7. Common Traps That Break UI Refactors

Trap 1: The "Vanishing Empty Folder"

If you build your card list purely by looping over recorded workouts, newly created folders will not render until an exercise is added. Always seed your card array with the known list of custom folders first.

Trap 2: The Orphaned View State

If a user deletes a sub-folder while viewing its contents, the screen will attempt to render a non-existent entity. In your delete handler, always check if (activeSubProfile === subName) setActiveSubProfile(null).

Trap 3: JSX Closing-Tag Cascades

Replacing large blocks of JSX often accidentally removes closing </div> tags from parent containers. Always edit inside out, verify with git diff, and run npm run build immediately.
